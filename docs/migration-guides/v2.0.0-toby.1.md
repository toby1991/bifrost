# Toby fork upgrade to Bifrost v2

## Frozen baseline

- Whole-tree base: `core/v1.8.4^{}` (`6d60595b574e5a89289e1449825d0854aa99eabb`).
- Official module lineage included by that base: Core `v1.8.4`, Framework
  `v1.6.0`, HTTP Transport `v2.0.0`. This is deliberately a Core-tag
  whole-tree snapshot, not an assembly of the three exact tag subtrees: it also
  contains the official Framework and Transport follow-up commits that landed
  between their own tags and `core/v1.8.4`.
- Existing fork tags are immutable: `core/v1.7.4-toby.7` and
  `framework/v1.5.4-toby.1` must not move.
- `helm-chart-v2.0.1` is a Helm chart release, not Bifrost HTTP `v2.0.1`.
- Do not create a `transports/v2.0.0-toby.*` module tag. The upstream v2 tag
  keeps the v1 module path (`github.com/maximhq/bifrost/transports`), so a v2
  module version cannot be consumed by normal Go module resolution.

## Capability preservation plan

- [x] Port and adapt provider lifecycle shutdown hardening.
- [x] Port and adapt configurable stale-connection retry layers, including
  private-network dialer and streaming-client behavior.
- [x] Port and adapt the dynamic-provider initialization switch.
- [x] Port Gate video generation, retrieval and download.
- [x] Keep Gate video edit, delete, list and remix explicitly unsupported.
- [x] Preserve Gate as a named-capable base provider and retain direct URLs in
  retrieval responses.
- [x] Add the v2 Provider surface required by Gate with explicit unsupported
  behavior where Gate has no operation.
- [x] Port the pure Framework chat-pricing API without catalog or Store lookup.
- [x] Adapt pricing to the nested `BifrostCost` result and the v1.6 pricing
  fields, including ultrafast token prices and per-request cost.
- [x] Allow Gate in the HTTP Transport configuration schema.

- [x] Run Gate race tests and the complete Gate provider package without live

- [x] Run Framework datasheet targeted and full package tests.

- [x] Validate the HTTP Transport Gate schema and its schema regression test.
- [x] Compile TokenEx's LLMGW pricing, provider, asset-route and execution

- [x] Review the final range diff against both fork tags and record any
  intentional upstream-semantic changes.
- [x] Add an opt-in, three-case Gate provider-harness chain in the review
  worktree: submit, bounded polling to `completed`, then content download.
  Validate JSON parsing, augmentation, chained variables and provider filtering
  without making a paid call. The harness-only diff remains unstaged for review,
  as required by the repository harness workflow.

The Gate harness partition is deliberately excluded from the default provider
roster because it creates a paid, long-running video job. `PROVIDER=gate` is an
explicit first-class path, the runner advertises the opt-in instead of silently
omitting it, and the integration config reads its credential from
`GATE_API_KEY`.

The TokenEx production packages compile against the upgrade. Its old golden
tests still encode two pre-upgrade Framework contracts: `BatchResultsRequest`
normalizes to unknown instead of the official v1.6 chat family, and the chat
pricing schema has 43 fields instead of the upgraded 48. Those assertions must
be updated when TokenEx switches its `go.mod`; they are not production compile
failures and are not hidden by this fork.

The complete TokenEx runtime suites were not reported green: their local
environment also requires Docker, bindable local ports and the repository's
database fixtures. The HTTP Transport executable likewise needs the generated
`ui` embed artifact that is not present in the source tag. Module compilation,
targeted unit tests and schema tests are the release evidence here.

## v2 deployment gates

- All three official module snapshots require Go `1.27.0`.
- Plugin custom URLs now require the v2 SSRF allowlist, and custom-path plugin
  create/update routes require admin authentication.
- Governance endpoints and pagination changed under `/api/governance/*`.
- `HTTPTransportPreHook` runs after authentication in v2; credential injection
  belongs in `PreAuthHook`.
- Some database migrations are forward-only. This source integration does not
  deploy the Gateway or run database migrations.
- `/v1/responses` remains available over ordinary HTTP JSON and SSE; WebSocket
  support is an additional transport, not a prerequisite.
